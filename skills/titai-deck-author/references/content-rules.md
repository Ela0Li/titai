# 内容规则：怎样写才不像机器拼的

协议只约束结构，不约束好坏。下面这些是从五个真实知识包（280 知识点 / 262 问答）里总结出来的写法，按「模块 → 知识点 → 问答 → 链接」排列。

## 模块：先回答「这组在考什么」

一个模块不是一个大标题，它要交代三件事：

1. `signal`：为什么这组重要、面试官在这里看什么
2. `keypoints`：这组的 3–5 个核心结论（不是目录）
3. `traps`：2–4 个常见错法

反例与正例：

```
✗ signal: "本模块介绍 C++ 的内存管理。"
✓ signal: "考的是你知不知道对象什么时候没的；答不出析构顺序，后面全是猜。"
```

```
✗ traps: ["注意内存泄漏"]
✓ traps: ["把 shared_ptr 当万能，循环引用时两个都释放不掉"]
```

模块标题的惯例是「模块一 · 内容」，序号给扫读用。模块数量 4–10 个；超过 10 个说明该拆包。

## 知识点：一句话 + 一条及格线

知识点是**掌握度的最小单位**：用户在列表页点三个圆点（未学/模糊/会/熟练），点的是这一条。所以：

- `text` 是陈述句，20–60 字，**一条只讲一件事**。两个概念并列就拆两条。
- 不写问句。问句属于问答。
- 不写任务（「掌握 X」「理解 Y」）——那是学习目标，不是知识。

```
✗ "深入理解多态的实现原理与虚函数表"
✓ "继承、多态、虚函数表、纯虚接口与虚析构的必要性"
```

`hint`（及格线）是这个包最值得花时间的字段，因为它决定了「我到底算不算会了」：

```
✗ hint: "掌握虚函数机制"                      （等于没说）
✗ hint: "虚函数表是一个指针数组，每个对象有一个 vptr，指向所属类的虚表……"  （这是答案，不是判据）
✓ hint: "能画出虚表指针，并说清基类析构为什么必须虚"
```

好 hint 的形状是「能说出/能画出/能举出 + 具体几条」。判据通常可以数：说出三条、举一个例子、画一张图。

## 问答：先定体裁，再定结构

### 判定体裁

按问题文本判断，顺序是从上往下第一条命中：

| 序 | 条件 | 体裁 |
|---|---|---|
| 1 | 含「区别／差异／异同／vs／对比」 | 对比型 |
| 2 | 含「怎么／如何／步骤／流程／实现」且不含「为什么／原理／本质／区别」 | 操作型 |
| 3 | 含「为什么／是什么／含义／意义／原理」 | 概念型 |
| 4 | 都不含，且很短（<12 字） | 快问型 |

### 四种结构模板

**概念型（最常用，仓库主用法）**

```json
[
  {"h": "结论", "p": "一句话给判断，先给答案再解释。"},
  {"h": "机制", "p": "为什么是这样：原理、数据流、关键不变量。"},
  {"h": "取舍", "p": "代价与边界：什么时候不成立，替代方案是什么。"},
  {"h": "实战", "p": "工程上怎么用/怎么排错，一到两句具体的。"}
]
```

**操作型**

```json
[
  {"h": "一句话", "p": "整体做法，包括最关键的判断点。"},
  {"h": "分几步", "p": "顺序不要乱的关键提示：", "list": ["第一步…", "第二步…"]},
  {"h": "边界", "p": "什么情况下这套做法会失效。"},
  {"h": "落地", "p": "在项目里怎么落地、验收标准是什么。"}
]
```

**对比型**

```json
[
  {"h": "一句话", "p": "两者的本质差别，一句话。"},
  {"h": "关键差异", "p": "差异集中在几个维度：", "list": ["维度：A 如何，B 如何"]},
  {"h": "怎么选", "p": "给判据：什么条件下选哪个。"},
  {"h": "边界", "p": "各自的失效场景。"}
]
```

**快问型**：2–3 块，「结论 + 一句展开」，或者「结论 + 边界」。**不要为了凑四段硬加取舍**。

### 写法要求

- 第一块（结论/一句话）只给判断，**不写过程**。写了「先…再…」就是体裁错配（体检规则 E4）。
- 「机制」要能自证：给出因果链或不变量，不要只说「因为设计如此」。
- 「取舍」必须承认代价。没有代价的方案通常是没想清。
- 「实战」写具体动作（看什么指标、先查哪里），不写口号（「要多实践」）。
- 一块一段，120 字以内；超过 260 字基本该拆。
- 有 3 个以上分号的长段，改成 `list`，每条一个维度（E5）。

### 长度与块数

- 概念型/对比型：3–5 块，总长 200–600 字
- 操作型：2–4 块 + 一个 `list`
- 快问型：1–3 块，总长 < 120 字

写不满时优先问：**这条问答到底该不该存在？**两条快问合并成一条对比型，比硬凑四段强。

## 覆盖与追问链

### 覆盖率

`covers` 要覆盖到知识点的 100%。两个理由：用户点开一个知识点发现没有题，会觉得包是残的；覆盖率也是自检——**覆盖不上的知识点往往是写得不清楚的那条**。

例外：纯清单类知识点（「常见面试流程」）可以挂在一条综合问答下，但别让一个问答覆盖十条。

### 追问链（`next` / `peer`）

- `next` 表达「答完这个，下一问会往哪挖」：结论 → 机制 → 边界 → 综合，`layer` 单调不减。
- `peer` 表达「同一层里容易被混的那一条」：`merge` 与 `rebase`、`shared_ptr` 与 `unique_ptr`。
- 每条问答最多 3 个方向；**只写单向**。App 会反向渲染，双向写会出现「互相被追问」。
- 链条密度参考：仓库里 262 条问答大约 300 条 `next`/`peer`，即平均每条 1.1 个方向。全是孤点说明包只是题库，没有网络。

### 跨包引用

只在两个包共享同一批概念时用（例如「方差与随机流」在数学包与 PCG 包里都出现）。跨包引用是**只读**的：默认不改对方进度。

## 语言与术语

- **术语统一到这份包自己的 `terms`**。如果一个包里叫「知识点」，就不要在正文里写「自查点」。
- 中文标点：句号用「。」，问句用「？」，并列用「、」，引号用「」或 “”。不要中英混用 `,` 和 `.`。
- 英文术语保留原形（`rebase`、`fBm`、`Perlin`），第一次出现时可加中文解释，之后不要反复解释。
- 不写「本文」「笔者」「众所周知」「简单来说」这类填充词。
- 数字用阿拉伯数字（3 条、120 字），量级单位用中文习惯（万、毫秒）。
- 不要在答案里写「见上文」「同上」——答案会被单独打开。

## 自查清单（交卷前逐条过）

- [ ] 每个模块都有 `signal`、`keypoints`、`traps`
- [ ] 知识点是陈述句、一条一件事、20–60 字
- [ ] 每个知识点有 `hint`，判据可数
- [ ] 覆盖率 100%，没有一条问答覆盖超过 5 个知识点
- [ ] 每条问答的体裁与结构对得上（跑 `audit-answers.js` 无命中）
- [ ] 结论块没有步骤；步骤块有 `list`
- [ ] 4 段以上都有小标题，层级不跳级
- [ ] `next`/`peer` 单向、方向合理、无孤点
- [ ] 没有再写 HTML 标签，公式用 `$…$`
- [ ] 术语在整份包里一致
