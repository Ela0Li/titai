# 题台知识包写作

题台是一个 Android 离线学习 App（仓库 `Ela0Li/titai`，包名 `com.studydeck.app`）。它所有的学习内容都是**纯 JSON 文件**，与引擎完全分离：写对 JSON，App 就能读；写错一个引用，导入就会被校验器挡下。

本技能的目标：让一个没有读过仓库的 agent，产出**一次导入就成功、内容结构站得住**的知识包或学习计划。

## 先判断要产出什么

| 用户想要 | 产出文件 | 命名 |
|---|---|---|
| 一个主题的学习内容 | 知识包 deck | `<deck-id>.json`，如 `rust-basics.json` |
| 几个包的组合学习路线 | 学习计划 plan | `<plan-id>.plan.json`，如 `ml.plan.json` |
| 往已有包里加题 | 改已有 deck.json | 保持原 id 与既有 id 命名 |

一个知识包是自包含的：模块（groups）→ 知识点（checks）→ 问答（qas）互相引用，**没有外部依赖也能导入**。学习计划只引用已安装的包的 `id`。

## 工作流（照顺序做，别跳）

### 1. 定范围与体量

先和用户对齐三件事：主题边界、目标水平、多少条。给一个默认体量参考（可按比例缩放）：

- 一个知识包：**4–10 个模块**，每模块 **6–12 个知识点**、**6–15 条问答**
- 知识点总数与问答总数大致 **1 : 1**（实测仓库里五个包是 280 知识点 / 262 问答）
- 问答分层：L1 打基础 ≈ 30%，L2 讲机制 ≈ 40%，L3 边界与实战 ≈ 25%，L4 综合 ≈ 5%

体量太小的包（<3 模块）在 App 里显得空，太大的包（>120 知识点）不适合一套复习计划。

### 2. 搭骨架：模块 → 知识点

先只写 `groups` 与 `checks`（不写问答），因为**知识点是掌握度的最小单位，问答是围绕它展开的**。一个模块要能回答「这组在考什么」：

```json
{
  "id": "m1", "title": "模块一 · 提交与分支", "short": "提交与分支",
  "priority": "P0", "stage": 1,
  "signal": "考的是为什么这样设计，命令记不住可以查，机制说不清就是没懂。",
  "keypoints": ["提交是快照", "分支是可变指针", "HEAD 指向当前分支"],
  "traps": ["把分支当目录副本", "对已推送的公共分支做 rebase"],
  "checks": [
    { "id": "m1.1", "text": "提交、分支、HEAD 三者的关系。", "lvl": "P0",
      "hint": "能画出提交链，并说清分支只是指针" }
  ]
}
```

写知识点的两条硬要求：

- `text` 是**一句话的知识点**（实测均值 23–31 字，最长不要超过 60 字），不是问句、不是任务清单。它是扫读单位，用户在列表页一眼扫过几十条。
- `hint` 是**及格线**：说到哪几条算过。只写判据，不复述答案，6–60 字，不换行。

### 3. 写问答：先定体裁，再定结构

这是最容易写砸的一步。答案**不再固定四段**（协议 v1.5 起自由结构），但「自由」不等于随便：结构要匹配问题的体裁。

| 问题体裁 | 触发词 | 答案结构（按顺序） |
|---|---|---|
| 概念型 | 为什么／是什么／含义／原理 | 结论 → 机制 → 取舍 → 实战（四段式，仓库主用法） |
| 操作型 | 怎么／如何／步骤／流程／实现 | 一句话 → 分几步（`list`）→ 边界／坑 → 落地 |
| 对比型 | 区别／差异／异同／vs | 一句话 → 关键差异（`list`，每条形如「维度：A 如何，B 如何」）→ 怎么选 → 边界 |
| 快问型 | 单点定义、数量、名词 | 结论 + 一句展开即可，2–3 块，别硬凑四段 |

块级写法：

```json
{ "h": "关键差异", "p": "两者的取舍集中在历史真实与历史干净之间：",
  "list": ["历史形状：merge 保留分叉，rebase 得到直线",
           "提交对象：rebase 会改写 hash"] }
```

- `p` 必填且 **≥ 8 字**，即使配了 `list` 也要写引导句（校验器 `E_ANS_P`）。
- `h` 自拟、≤ 24 字；`lvl` 是标题层级 1–3，**不能跳级**，没有 `h` 就不要写 `lvl`。
- 一段 `p` 控制在 120 字内，超过 260 字基本该拆；`list` ≤ 10 条、每条 ≤ 200 字。
- 长答案（>3 块）要给小标题，否则 `W_ANS_NOHEAD`。

详细规则与反例见 `references/content-rules.md`。

### 4. 连引用：覆盖 + 追问链 + 参见

- `covers`：这条问答覆盖了哪些知识点 id（必填、非空）。**目标覆盖率 100%**，`W_UNCOVERED` 会列出漏掉的知识点——它是警告不是错误，但漏覆盖意味着那个知识点在 App 里点进去没有题。
- `next`：往下追问的方向（最多 3 条）；`peer`：同级对比方向（最多 3 条）。App 会自动反向补出「被追问／被对比」，所以**只写单向**，不要两边都写（双向会触发 `W_CYCLE`）。
- `next` 指向的问答 `layer` 应 ≥ 当前层，否则 `W_LAYER_DOWN`——追问不该越问越浅。
- 跨包引用写成 `deckId#localId`，如 `"ue5-pcg#q.m2.noise"`。只在用户明确要联包时用；目标包没装时 App 会显示为灰色不可点。

### 5. 跑校验，循环到全绿

```bash
node scripts/check.js my-deck.json                # 校验 + 答案体检，一条命令
node scripts/validate-deck.js my-deck.json        # 只校验
node scripts/audit-answers.js my-deck.json        # 只看答案结构
node scripts/check.js my.plan.json --decks ./decks  # 计划，顺带核对成员包存在
```

**没跑通 `check.js` 就不要把文件交给用户。** 退出码 0 才算过。错误码含义与修法见 `references/validation.md`。输出里 `problems` 必须清零，`warnings` 尽量清零；`notes`（`W_CYCLE` / `W_LAYER_DOWN`）只是提示，不拦导入。

上面写的是「在技能目录下」的调用方式；如果你在别处写内容，用绝对路径调用脚本即可，脚本本身不依赖工作目录：

```bash
node <技能目录>/scripts/check.js /abs/path/my-deck.json
```

### 6. 交付

告诉用户三件事：文件路径、这个包里有什么（模块数／知识点数／问答数／覆盖率）、怎么装进去：

> 手机 App → 设置 → 从文件导入 → 选 JSON；或者手机连电脑后 `adb push my-deck.json /sdcard/Download/` 再在 App 里选。

如果是替换自己维护的包，提醒一句：**同一个 `id` 的包会被覆盖，学习进度按 `id` 存，覆盖后进度保留**；换了 `id` 就是新包，进度从 0 开始。

## 硬规则速查

| 层 | 规则 |
|---|---|
| 顶层 | `schema: 1`；`id` 匹配 `^[a-z0-9][a-z0-9-]{1,40}$`；`title` ≤ 120；`accent` 形如 `#3b82f6` |
| terms | 可选，改界面称呼：`group/check/qa` 各 ≤ 8 字，缺省「模块/知识点/问答」 |
| group | `id` 匹配 `^[A-Za-z][A-Za-z0-9_-]{0,15}$`；`priority` ∈ P0/P1/P2；`stage` 1–4；`signal`/`keypoints`/`traps` 缺失只警告但**应该写** |
| check | `id` 必须 `groupId + "." + 数字`（如 `m1.3`），否则 `E_CHECK_PREFIX`；`text` 4–300 字；`lvl` ∈ P0/P1/P2 |
| qa | `id` 形如 `q.m1.merge`；`m` 必须等于某个 group 的 id；`layer` 1–4；`q` 以 ？ 或 。 结尾（缺了是 `W_QA_MARK` 警告）；`tags` ≤ 6 个 |
| ans | 1–12 块；每块 `p` ≥ 8 字；标题 `h` ≤ 24 字，`lvl` 1–3 且不跳级 |
| 引用 | 本地引用只能指向本包已有 id；`covers` 指向 check，`next`/`peer`/`seeAlso` 指向 qa；**不能引用自己**（`E_SELF_REF`） |

`seeAlso` 是知识点的「顺带看」，**指向问答**而不是别的知识点（这是最常写错的一条）。

上表里 `title`/`subtitle`/`tags` 的字数、`terms` 三项同写、`stage` 单调、`next`/`peer` ≤ 3 属于协议约定，**校验脚本不查**（schema 管，但不影响导入）；脚本拦的是结构塌坏与引用闭合。分清这两类，能省掉反复试的功夫。

## 常见返工清单

写之前扫一眼，这八条占实际返工的九成：

1. `covers` 写了知识点 id 之外的东西，或指向不存在的 id → `E_COVER_REF`
2. `next`/`peer`/`seeAlso` 指向知识点而不是问答 → `E_QA_REF`
3. 答案块 `p` 写空串，想只用 `list` → `E_ANS_P`（引导句是必需的）
4. 小标题写了 `lvl: 2` 但前面没有 `lvl: 1` → `E_ANS_LVL`
5. 操作型问题套了「取舍／实战」四段式 → 结构不匹配，答案体检 `E3`
6. 结论块里写步骤（先…再…）→ 结论应只有判断，过程放「分几步」
7. 知识点写成问句或任务（「讲清 X」）→ 知识点是陈述句的知识单元
8. 覆盖率留着 70% 就交付 → 用户点进去会发现空档
